# Authoritative Register Map

## Scope

This document is the current software-visible register contract for the protection IP before PYNQ-Z2 bring-up. It applies to both access paths:

| Access path | RTL top | Notes |
|---|---|---|
| Internal simulation bus | `protection_ip_top_reg_controlled` | One-cycle `wr_en` / `rd_en` pulses into `protection_reg_bank` |
| AXI-Lite wrapper | `protection_ip_top_axi_lite` | AXI-Lite slave wrapper around the same register bank |

The canonical implementation is `rtl/protection_reg_bank.v`. AXI-Lite byte addresses are identical to the internal register offsets below.

## Register Summary

| Address | Name | Access | Reset / default | Bits | Description |
|---:|---|---|---:|---|---|
| `0x00` | `CTRL` | RW / W1P | `0x0000_0000` | `bit0 pwm_enable`, `bit1 clear_fault_pulse` | Enables demo PWM and issues a one-clock fault-clear request |
| `0x04` | `STATUS` | RO | live, reset `0x0000_0000` | `bit0 fault_valid`, `bit1 fault_latched` | Current raw and latched protection state |
| `0x08` | `FAULT_CODE` | RO | live, reset `0x0000_0000` | `bits7:0 fault_code_latched` | Latched fault reason from the FSM |
| `0x0C` | `I_CH1` | RO | live | `bits11:0 i_ch1 monitor` | Channel 1 current monitor |
| `0x10` | `I_CH2` | RO | live | `bits11:0 i_ch2 monitor` | Channel 2 current monitor |
| `0x14` | `TH_OC1` | RW | `3000` | `bits11:0 threshold_ch1` | Channel 1 over-current threshold |
| `0x18` | `TH_OC2` | RW | `3000` | `bits11:0 threshold_ch2` | Channel 2 over-current threshold |
| `0x1C` | `TH_DIFF` | RW | `200` | `bits11:0 diff_threshold` | Channel mismatch threshold |
| `0x20` | `PWM_PERIOD` | RW | `1000` | `bits15:0 pwm_period` | Low-voltage demo PWM counter period |
| `0x24` | `PWM_DUTY` | RW | `500` | `bits15:0 pwm_duty` | Low-voltage demo PWM high-time count |

There is no standalone clear register at `0x20`. There is no base version register at `0x24`. There is no base gate-inhibit mask register field.

## Naming Rules

The canonical register names are the uppercase names in the table above: `CTRL`, `STATUS`, `FAULT_CODE`, `I_CH1`, `I_CH2`, `TH_OC1`, `TH_OC2`, `TH_DIFF`, `PWM_PERIOD`, and `PWM_DUTY`.

Use these naming rules when updating RTL, testbench, software headers, or documents:

1. `TH_OC1` and `TH_OC2` are the register names. `threshold_ch1` and `threshold_ch2` are field descriptions, and the RTL signal names are `th_oc_ch1` and `th_oc_ch2`.
2. `pwm_enable` is the `CTRL[0]` field name. The lower-level `pwm_gen` module has a local port named `enable`, but software-visible documentation should call the register bit `pwm_enable`.
3. `clear_fault_pulse` is the `CTRL[1]` field behavior. Short prose may say clear request, but it must not imply an unconditional unlock of `fault_latched`.
4. Any future version/build register is an optional extension and is not part of the base address map.

## Field Details

### `0x00 CTRL`

| Bit | Field | Access | Reset | Behavior |
|---:|---|---|---:|---|
| `0` | `pwm_enable` | RW | `0` | `1` enables the low-voltage demo PWM carrier before protection gating |
| `1` | `clear_fault_pulse` | W1P, reads as `0` | `0` | Write `1` to request one clock of fault-clear pulse |
| `31:2` | reserved | RO | `0` | Reads as zero |

`clear_fault_pulse` is generated by writing `CTRL[1] = 1`. The pulse is asserted for one clock in `protection_reg_bank` and is automatically cleared on the next clock. Readback of `CTRL[1]` is always zero because it is a pulse request, not a stored mode bit.

The clear request does not override a still-present fault. If the current fault condition remains active, the FSM keeps or re-enters `fault_latched` and the protected output remains asserted. A clear request can recover the latched state only after the input condition has returned to a safe range and the FSM has completed its reset-wait behavior.

### `0x04 STATUS`

| Bit | Field | Access | Reset | Behavior |
|---:|---|---|---:|---|
| `0` | `fault_valid` | RO | `0` | Raw current-cycle fault indication from the classifier |
| `1` | `fault_latched` | RO | `0` | Latched protection state from the FSM |
| `31:2` | reserved | RO | `0` | Reads as zero |

`fault_valid` may deassert when the instantaneous input returns below threshold. `fault_latched` remains asserted until the FSM accepts a valid clear request while the fault condition is no longer present.

### `0x08 FAULT_CODE`

`FAULT_CODE[7:0]` reads `fault_code_latched`. Fault-code values are defined by `rtl/fault_defs.vh` and are produced by the classifier/FSM path.

### `0x0C I_CH1` and `0x10 I_CH2`

`I_CH1[11:0]` and `I_CH2[11:0]` are live monitor readbacks of the current input samples. Upper bits read as zero. They are read-only and intended for simulation, software debug, and later board-level observation.

### `0x14 TH_OC1`, `0x18 TH_OC2`, and `0x1C TH_DIFF`

Threshold registers store the low 12 bits of write data. In the current comparator RTL:

```text
over-current is true when current > threshold
mismatch is true when abs(i_ch1 - i_ch2) > diff_threshold
```

Therefore equality to a threshold is not a fault in the present implementation.

### `0x20 PWM_PERIOD` and `0x24 PWM_DUTY`

PWM registers store the low 16 bits of write data. They drive the low-voltage demo PWM carrier in `pwm_gen`.

Boundary behavior in the current RTL:

| Condition | Current behavior |
|---|---|
| `pwm_enable = 0` | `pwm_raw` is held low |
| `PWM_PERIOD = 0` | `pwm_raw` is held low |
| `PWM_DUTY = 0` | `pwm_raw` remains low during enabled operation |
| `PWM_DUTY >= PWM_PERIOD` | Duty is clamped to the period, so the waveform is effectively always high while enabled and period is nonzero |
| `fault_latched = 1` | `pwm_out` is forced to the safe low level by the protection gate |

The PWM registers are only for an observable low-voltage demonstration carrier. They are not a full motor-control PWM subsystem.

## Future Optional Registers

Future stages may add optional registers such as `VERSION`, build metadata, board debug, or explicit protection-output controls. Those registers are not part of the current base contract and must not reuse `0x20` or `0x24`, which are already assigned to `PWM_PERIOD` and `PWM_DUTY`.

Any future register extension must update RTL, testbench, software headers, and this document in the same change.
